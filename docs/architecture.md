# Architecture

## Pieces

| piece | where | job |
|---|---|---|
| `adl-signer` | Lambda (`bootstrap`) or EC2 (systemd) | the API; one binary |
| CA keys | KMS, one asymmetric key per environment (RSA-4096 default) | sign device certs and CRLs |
| registry | DynamoDB, single table | devices, certs, chip claims, the ID counter, audit events, auth nonces |
| archive | S3, versioned + Object Lock | every cert/chain PEM, CRLs, CA chains, escrowed dev keys |
| `adl` | developer laptops, factory stations, admin machines | client |

The server is stateless. Everything lives in KMS, DynamoDB and S3. That's
what lets Lambda and EC2 run side by side against the same data, and why
switching modes is a Terraform variable rather than a migration.

## Request flow (issue)

```
adl                                   adl-signer                          AWS
 | generate key + CSR locally
 | sign sts:GetCallerIdentity  ------>  verify token shape, audience,
 | (audience, nonce, body hash)         request digest, timestamp
 |                                      replay to STS ----------------->  STS: who is this?
 |                                      claim nonce (DynamoDB, TTL)
 |                                      role -> permissions (auth policy)
 |                                      validate CSR, chip, labels
 |                                      allocate GLXADL id (atomic ADD) >  DynamoDB
 |                                      sign cert ---------------------->  KMS Sign (digest)
 |                                      verify signature locally
 |                                      archive cert/chain(/key) ------->  S3 (SSE-KMS)
 |                                      record cert, update device ----->  DynamoDB
 |                                      audit event -------------------->  DynamoDB + logs
 | <----------------------------------  cert + chain
 | write files / flash device
```

## Authentication

There are no API keys. Callers prove who they are with the AWS credentials
they already have:

- The client signs an `sts:GetCallerIdentity` request with SigV4. The
  signature covers three extra headers: `X-Adl-Audience` (this deployment),
  `X-Adl-Nonce` (random) and `X-Adl-Request-Digest` (SHA-256 of method, URI
  and body of the *actual* API call).
- The server checks those, then sends the signed request to STS itself,
  always to its own regional STS URL and never to a URL the client supplies.
  STS answers with the caller's ARN only if the signature is genuine.
- The nonce is then claimed in DynamoDB, so each token works once.
- The role name (or IAM user) is mapped to permissions by the auth policy
  (`ADL_AUTH_POLICY`, generated by Terraform). Glob patterns let you bind
  IAM Identity Center permission sets, e.g. `AWSReservedSSO_ADLDeveloper_*`.

A captured token is useless against another service (audience), for another
request (digest), a second time (nonce), or after five minutes (timestamp).

### Permissions

| permission | lets you |
|---|---|
| `<env>:issue` | sign CSRs in that env (new devices, or re-issue unconfirmed ones) |
| `<env>:read` | list/show devices, fetch certs and chains |
| `<env>:key-read` | fetch escrowed private keys (audited) |
| `<env>:provision` | confirm EoL provisioning |
| `<env>:revoke` | revoke, and re-key already provisioned devices |
| `ca:admin` | CA CSR and install |
| `admin:import` | import legacy certs, pin counter ids |
| `audit:read` | read the audit log |

Recommended: bind IAM Identity Center permission sets with `auth_bindings`.
AWS sets the role session name to the person's username, so the audit log
shows who really did it. Optionally (`create_client_roles = true`) Terraform
also creates `adl-developer` -> `dev:issue dev:read dev:key-read`,
`adl-factory-station` -> `prod:issue prod:read prod:provision` and
`adl-ca-admin` -> `*`. Those roles are assumable only by the principals you
list (and, for the station role, by IAM Roles Anywhere trust anchors).

## Device identity rules

- Device IDs come in two schemes, set per environment. With a counter,
  IDs are the prefix plus a number (`GLXADL017`) from an atomic counter
  shared by every environment with that prefix, so dev and prod never
  hand out the same number; only admins can pin one, and imports move the
  counter past whatever they bring in. With `device_id_from_chip`, the ID is
  the prefix plus the chip's MAC (`GLXADL3C71BF4A12E0`): a board gets the
  same ID from every signer and stage, without them sharing anything.
- Within an environment, a chip MAC is claimed by exactly one device (a
  conditional write in a DynamoDB transaction). Claims are per environment,
  so a dev cert can't squat on a production chip. Prod requires a chip ID
  on every cert.
- Re-issuing revokes the previous cert as `superseded`. A device that's
  already `provisioned` can only be re-keyed by someone with `revoke`.
- Device cert profile: `O=<organization>, CN=<device id>`, clientAuth, digitalSignature (+keyEncipherment for RSA),
  10 years (clamped to the intermediate), random 127-bit serial.

## Lambda or EC2?

Both run the identical handler. Pick per deployment:

| | Lambda + API Gateway | EC2 + ALB |
|---|---|---|
| cost at this volume | cents/month | ALB + 2x t4g.small, roughly $40-50/month |
| patching | none | AMI refresh (instance refresh is wired up) |
| cold start | ~300-500 ms on first call | none |
| private-only access | possible via private API, not wired here | `internal_alb = true` behind VPN/Direct Connect |
| fixed IP allow-listing | no | ALB SG `allowed_cidrs` + WAF |
| WAF | no (HTTP APIs) | yes, rate limit + AWS managed rules |

A sensible default is Lambda. Choose EC2 if the factory network has to
reach the service over a private link, or the company's policy wants a
WAF in front. `deployment_mode = "both"` is also valid, for example Lambda
for developers on the internet plus an internal ALB for the factory, with
shared data.

## What gets stored where

```
s3://<archive>/
  certificates/<env>/<device>/<serial>/certificate.pem
  certificates/<env>/<device>/<serial>/chain.pem
  escrow/<env>/<device>/<serial>/private-key.pem   (escrow KMS key, dev only)
  ca/<env>/chain.pem                                 current intermediate + root
  ca/<env>/history/<fingerprint>.pem                 every chain ever installed
  ca/<env>/current.crl
```

DynamoDB item layout is documented at the top of `internal/store/dynamo.go`.
